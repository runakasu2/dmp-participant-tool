# 勝率分析

## 画面・変更ファイル

独立ページ「勝率分析」を追加。PCはサイドナビ、スマートフォンは「その他」から開く。デッキメモの画面や保存仕様は変更していない。

- `winrate-analysis.js`：読み取り専用API、入力検証、現在のメモとの結合、重複排除、集計。
- `winrate-ui.js`：大会・期間・形式・提供サイトのフィルター、並び替え、マトリクス、詳細。
- `index.html`：ページとナビゲーション。
- `script.js` / `workspace-ui.js`：既存方式でのページ切り替えと現在ページ表示。
- `server.js`：新しいGETルートの登録。
- `style.css`：このページに限定したレスポンシブ表示。
- `tests/winrate-analysis.test.js`：純粋集計のテスト。
- `tests/winrate-postgres.integration.js`：独立したPGliteでのDB/APIテスト、ブラウザ用データ。
- `tests/winrate.browser.cjs`：ローカルChromeによる画面テスト。
- この文書：仕様と検証・反映手順。

画面は条件選択、集計件数、対象外の内訳、デッキ別成績、対面マトリクス、選択した対面の詳細の順。デッキ別成績は試合数・勝率の降順またはデッキ名順に並び替える。マトリクスは横スクロールし、デッキが20種類を超える場合は縦軸・横軸をそれぞれ20件単位で切り替える。詳細は50試合単位で表示し、保存済み対戦表の該当ラウンドへ移動できる。

## 読み取り専用API

- `GET /api/winrate/events`：保存済み対戦表があるDMP大会一覧。名前、日付、フォーマット、提供サイト、3項目の大会キーを返す。
- `GET /api/winrate/summary`：大会一覧、デッキ別成績、疎な対面集計、排他的な除外件数、重複件数、集計リビジョン。
- `GET /api/winrate/matchup`：同じ集計処理による対面成績と個々の試合。追加条件は `deckId`, `opponentDeckId`, `page`（1から）, `pageSize`（1〜100、既定50）, `revision`。

summary / matchup 共通条件：`mode=all|single`（既定all）、`eventRecordId`（singleで必須）、`startDate` / `endDate`（実在するYYYY-MM-DD、両端を含む）、`format=original|advance|2block|unknown`、`provider=nojigiku|tcg_meister|sugatool`。形式・提供サイト・期間は省略で制限なし。開催日未登録の大会は期間を指定すると対象外となる。

大会IDは `events.id` を参照し、その既存一意キー `ShopID + EventID + Seq` を維持する。外部サイトのIDは `provider + source_key` として別に扱う。

全APIは `REPEATABLE READ READ ONLY` トランザクションを使用。条件は検証してプレースホルダーへ渡す。対戦表・メモ・カタログを一括取得し、試合ごとのSQL往復や外部サイト取得はしない。現在のアプリと同じアクセス制御を使用する（既存サーバーには認証ミドルウェアがない）。レスポンスは `Cache-Control: no-store`。

summary と matchup のデータ変更を検出するため、読み取りデータのSHA-256リビジョンを返す。詳細要求のrevisionが異なる場合は409とし、UIは再集計してセルの再選択を案内する。取得エラーを空の正常結果として扱わない。

## 集計単位・除外・重複

勝率は `勝利 / (勝利 + 敗北) * 100`。`win_loss`で双方の異なる参加者キーがあり、winner_keyが一方を指す正常な試合のみ採用。Bye、double_loss、unresolved、未知の結果、不正な勝者キーは勝率に含めない。勝敗の推測・得点からの追加復元はしない。3サイトとも既存の正規化済み保存結果を使用する。

デッキ別表の「試合数」はそのデッキの使用者成績数（勝＋敗）。ミラーの物理1試合は2人分の成績なので、表に1勝1敗・試合数2を加える。APIにはデッキごとの物理試合数 `physicalMatches` もある。試合数ゼロのrateはnullで、UIは「—」。通常試合で片側のデッキのみ判明した場合、判明した側のデッキ別成績には含める。

対面表は両側のデッキが判明した通常試合のみ。非ミラーは両方向のセルへ同じ物理試合を記録し、逆方向は勝敗を反転。ミラーセルは物理試合数1・1勝1敗・50%。詳細はミラーでも1試合1行であり、セルと同じ成績を返す。セルの合計は逆方向にも同じ試合があるため、全体の物理試合数とは異なる。

保存元の結果または同一参加者の既知デッキが競合すると、その物理試合を「その他」に分類。競合以外は Bye → 両者敗北 → 未判定 → 不正な通常試合などのその他 → デッキ未登録の順に排他的に分類する。

- `savedRecords - duplicatesRemoved = uniqueMatches`
- `matchupMatches + excludedMatches = uniqueMatches`
- `normalMatches` は片側／両側デッキ不明の正常試合も含む。
- `deckPlayerObservations` はデッキ別表の試合数の総和。
- `dedupConflicts` は「その他」の内数。

同じDMP大会・回戦・双方の実DMP IDで確実に同じ試合と判定できる場合、提供サイトをまたいで重複排除する。1人のByeも実DMP IDで重複排除。DMP IDなしの場合は、同じ大会・回戦・提供元・外部大会ID内の確実な参加者キーだけを使用する。席番号や不確かなキーはarchive / round / match_keyの範囲を越えて統合しない。名前による統合、TCG内部番号とDMP IDの同一視はしない。明確な勝敗のコピーを未判定のコピーより優先し、同じ結果なら既知デッキ数が多いコピーを選ぶ。矛盾する結果は優先順位で隠さず除外する。

## 現在のデッキメモとの連携

`matching_archives.event_record_id + provider + source_key` に対応する `deck_memo_events` を参照。実DMP IDがある側はdeck_memosのDMP ID、ない側はdeck_memo_external_playersの参加者キーで照合する。TCGの外部参加者キャッシュにある旧DMP対応候補は実DMP IDへの変換には使わない。

ライブメモが存在する場合は、明示的な空選択も含めて最優先。ライブメモがない場合のみ、同じ大会・同じ提供元・同じ外部大会IDのdeck_memo_archives / deck_memo_archive_playersを使う。過去大会の履歴、他サイトの未照合メモ、対戦表保存時に埋め込まれた古いデッキ名は補完に使わない。

正式デッキIDで集計するため、既存の別名経由で選択・保存されたデッキも同じデッキに統合される。集計関数で名前を受け取る場合は既存カタログと同じ完全一致・大小文字無視・正式名優先・ID順の別名解決を行う。名称の類似や独自の空白正規化で統合しない。プレイヤー名の前後スペースはそのまま表示し、照合は名前を使わない。

ページを開くたび、条件変更時、再集計ボタンで現在のメモから計算する。集計結果の保存テーブルや書き込みAPIはない。

## 検証と本番反映前の確認

ローカルNodeテストと既存PostgreSQL相当テスト、勝率分析ブラウザテスト、既存ののじぎく・TCGマイスター・スガツール保存／デッキメモとワークスペースのブラウザ回帰テストを実行する。最終結果はNodeテスト275件すべて成功、4つのブラウザテストすべて成功。PGliteテストは独立したメモリDBのみで、本番の環境変数やNeonを参照しない。画面幅375 / 390 / 430 / 768 / 1440pxを確認する。

DBスキーマ・既存データ・既存APIの変更、マイグレーション追加／実行はなし。Git commit / push / Renderデプロイはしない。

本番反映前は既存013までの対戦表関連スキーマが適用されていることを確認し、バックエンドとフロントエンドの全変更を一緒に反映する。実際の保存件数で集計応答時間を確認し、代表大会について対象／対象外件数、同一IDの重複排除、メモ変更と詳細の整合性を確認する。今回の機能のためのDB作業は不要。

既知の制約：確実な共通IDを持たない異なる提供サイトの対戦は統合できず、複数保存元を選ぶと残る可能性がある。提供サイトフィルターを使って範囲を確認できる。1人の使用デッキは大会内全ラウンド共通であり、途中で変更したデッキをラウンド単位に推測して配分しない。大量データの実運用負荷・本番データそのものとの照合は未実施。マトリクス全セルの一括表示／エクスポート、集計結果の永続化、自動外部取得は対象外。
