# パフォーマンス改善・検証記録（2026-10-24）

## 計測条件

本番Neon・外部サイトには接続せず、PGliteの隔離DBで120大会、デッキ履歴7,680件、対戦15,360件を生成しました。改善前・後を交互に3回実行し、各回はウォームアップ後5回の中央値、その3回の中央値を採用しています。改善後は追加インデックス015を隔離DBへ適用しています。PGliteではCONCURRENTLYを除去して同じインデックスを作成し、本番での並行構築・ロック動作は再現していません。

これはDB＋Nodeの処理時間です。HTTP転送・Neonの通信待ち・実サイト取得時間・本番初期表示は含みません。絶対値や改善率を本番性能へそのまま適用できません。小さな差は実行揺らぎです。プレイヤー検索SQLと母数集計SQLは変更しておらず、この2項目では処理時間の改善を確認できていません。母数SQLの書き換え案は実測で効果が確認できなかったため採用しませんでした。

| 対象 | 改善前 | 改善後 | 改善率 | SQL発行数（トランザクション制御含む） |
|---|---:|---:|---:|---:|
| 大会一覧取得 | 87.71 ms | 4.27 ms | 95.1% | 1 → 1 |
| 母数推移取得 | 73.01 ms | 73.89 ms | -1.2% | 2 → 2 |
| 勝率分析 | 372.41 ms | 348.62 ms | 6.4% | 6 → 6 |
| プレイヤー検索 | 0.62 ms | 0.63 ms | -1.6% | 1 → 1 |
| 大会結果保存（128人） | 59.57 ms | 4.91 ms | 91.8% | 259 → 5 |

大会一覧・推移・勝率サマリー・プレイヤー検索の返却内容は、改善前後のハッシュが一致しています。JSONの詳細は `performance-results.json` に記録しました。大会結果保存は別途、実DBテストで順位・元順位文字列・更新・欠落レコード保持・失敗時の全体ロールバックを検証しています。

## 調査結果と実装

- 大会結果保存はプレイヤーごとに2クエリを発行していました。一括UPSERTに変更し、128人で259回から5回へ削減しました。入力全体の検証、同一大会ロック、トランザクション、順位不明、同じ大会の再取得時に欠落したプレイヤーを残す仕様は維持しています。
- 大会一覧の結果件数集計が検索範囲外の大会も走査していました。選択された大会集合へ制限しました。大会・プレイヤー・最新履歴を照合する複合インデックスを追加するSQLも用意しました。
- 勝率サマリーでも全対戦の両方向の詳細オブジェクトを作成し、最後に破棄していました。サマリーと検索詳細では不要な対面詳細を生成せず、対面詳細APIは指定対面だけ生成します。集計・重複排除・競合検出・revision・除外ルールは維持しています。DB問い合わせ回数は変更していません。
- プレイヤー詳細の履歴・じゃんけん集計・あいこ分析は、プレイヤーID確定後に独立して並列取得します。取得内容・クエリ数は変更しません。この処理単体の改善時間は未計測です。
- 大会名の一覧絞り込みは即時のまま、開いている母数・推移分析の再取得を180msデバウンスします。古い結果はバージョンで破棄し、推移・期間集計・勝率サマリーの古いfetchもAbortControllerで中止します。ブラウザの中止がDB側クエリの停止を保証するものではありません。
- 保存一覧は日時を各レコードで一度だけ評価して並べ替え、行DOMを現在ページと前後ページに限定します。ページ数・全件参照・並び順・ボタン操作は維持します。
- 同一のShopID＋EventID＋Seqの公開参加者取得は、同じfetchクライアントで処理中の場合だけ共有します。各呼び出し元には別配列・別レコードを返します。完了後・エラー後は直ちに削除し、次の取得は必ず再取得します。既存の総30秒タイムアウト・ページ数上限は維持します。レガシー参加者取込もこの処理と一括保存を再利用します。
- DMP大会詳細のHTML取得に15秒のタイムアウトを追加しました。TCGのCookie分離・文字コード・ページ遷移、スガツールの既存並列取得・期限、のじぎくの空レスポンス保護は変更していません。外部同時接続数を増やす変更や追加リトライはしていません。

## ブラウザ計測

ローカルChromeと隔離DBで、母数・推移を開いた状態で大会名を5回連続変更した際の分析リクエストは10回から2回（80%削減）でした。

保存一覧2,000件を全200ページ巡回した結果、参照できた件数は前後とも2,000件です。巡回後の行DOMは2,000件から20件（最大30件）へ削減しました。3回の巡回処理中央値は58.60msから60.10msで、処理時間の改善は確認できません。主な効果はDOM保持量の削減です。記録は `performance-ui-results.json` を参照してください。

## キャッシュ方針

DB検索結果のTTLキャッシュは追加していません。保存・編集・削除後の再取得は毎回DBから読み直します。公開参加者取得の共有は「実行中のみ」であり、完了後の有効期限はありません（保持しません）。キーは完全な大会キーとfetchクライアントで分離します。追加の有料サービスや永続キャッシュは不要です。

## 確認した範囲・残課題

初期HTML/CSS/JS、API登録、一覧・検索・母数、勝率、参加者・公式結果取込、プレイヤー詳細、保存済みメモ・対戦表、各提供元の取得を確認しました。

- 本番のAPIレスポンス時間、Neonの実行計画・ネットワーク遅延、外部HTTP、初期表示時間、参加者取得全体、公式結果取得全体、プレイヤー詳細単体、個別大会母数単体の時間は未計測です。
- 初期表示は既存のローカル資産構成を維持しました。計測で裏付けられない遅延読込や大規模なモジュール分割は行っていません。
- 大会カード・検索結果・保存アーカイブのメタデータは全件取得が残ります。大量化時には別途計測してページ単位の取得を検討できますが、今回はAPI互換性を優先しました。
- 母数推移と期間集計は別APIのため、両方を開く場合の集計重複は残ります。デバウンスにより不要な繰り返し取得を削減しています。
- 勝率分析は対象大会の対戦を読み込んでNodeで集計します。さらに大規模なデータへの対応には、既存の重複・競合・ミラー・デッキ未判明の規則を保った追加検証が必要です。
- プレイヤー名の部分一致は既存SQLを維持しました。今回のデータ量ではボトルネックではありません。拡張機能導入やtrigramインデックスは追加していません。

## 本番反映

本番DBへのSQL・計測、Git commit・push、Renderデプロイは実行していません。テーブル・カラムの変更、既存データの削除・初期化もありません。

一覧の大幅な短縮は追加インデックス適用後の計測です。コードだけでも動作しますが、本番で同じインデックス効果を得るには手動適用が必要です。

1. 適用対象DB・スキーマとバックアップ／復旧方法を確認してください。
2. SQLクライアントの自動コミット状態で `migrations/015_performance_indexes.sql` を単独実行してください。`CREATE INDEX CONCURRENTLY` を `BEGIN` / `COMMIT` やマイグレーションツールのトランザクションで囲まないでください。包括的な `/api/setup-db` を本番で呼ぶ必要はありません。
3. 対象スキーマの `pg_index` / `pg_class` を参照して `deck_history_event_player_recent_idx` の `indisvalid` と `indisready` がtrueであることを確認してください。途中失敗で無効な同名インデックスが残った場合、IF NOT EXISTSは再構築しないため、自動再試行せずそのインデックスの状態を確認してください。
4. 通常のRenderデプロイ手順で反映し、一覧・結果保存・検索・デッキメモ更新後の再集計を確認してください。新規環境変数・新規依存パッケージ・有料サービスは不要です。
